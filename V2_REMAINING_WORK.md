## Priority 0 — Correctness bugs (not missing features; the mechanism is built and behaves wrong)

1. **[RESOLVED 2026-11-12]** **Fix H-1: stale `focusState` is not reset on any navigation path except the Dock's own click handler.** [app.js:86-90](scripts/app.js#L86-L90),[117-124](scripts/app.js#L117-L124). Two candidate fixes identified during the audit (not applied, per audit-only scope): reset `focusState` at the top of `renderRoute` whenever `activeDestination` changes from its previous value, or move the reset into `TwmRouter.navigate` itself so every navigation path resets it uniformly. This single fix resolves: the Admin ⌘K navigation break, the ordinary-usage SMC-connect-then-navigate break, the Command Centre tile-click break, and the generic back/forward break — four of the five reproduction paths documented in Phase 2/6.
2. **[RESOLVED 2026-11-12]** **Fix the event-bubbling sub-case of H-1 specifically** — add `event.stopPropagation()` to `wireConnectButtons()`'s nested button handler in [client.js](scripts/content/client.js), or add an `event.target === panelEl` guard to the panel-level click listener in [stage.js:43](scripts/stage.js#L43). This is the single most severe reproduction path because it is triggered by completely ordinary use (connect SMC account, then switch tabs), not a contrived sequence. Should be fixed together with #1 since both touch the same code paths.
3. **[RESOLVED 2026-11-12]** **Fix Admin's phone-width dock overflow (P6-12).** [layout.css:82-99](styles/layout.css#L82-L99) — `.twm-dock` has no `overflow-x`, `flex-wrap`, or item-shrink rule, and is centered via `transform: translateX(-50%)`, so a 6-item dock (Admin) overflows a 375px viewport on both edges while 5-item docks (Client/Employee) don't. Candidate fixes: allow the dock to shrink item padding/font-size below a breakpoint, allow horizontal scroll within the dock container, or reduce visible labels to icons-only below a width threshold.

## Priority 2 — Individual-record data model (blocks a large cluster of Focus/Immersive requirements in Employee)

8. **[RESOLVED 2026-11-12]** **Introduce an individual Lead/Customer/Application/Task record concept.** Every CRM/Applications/Tasks Focus-mode requirement that says "selecting a lead/customer/application/task expands its detail" (P4-25, P4-27, P4-29) is NOT IMPLEMENTED for the same root reason: there is no list of individual, selectable records anywhere in the data model — only panel-level categories. This is a genuine data-model decision (even mock/fixture data, honestly labelled as illustrative, would suffice for a frontend-only prototype) — currently the honesty rule is honored (no fake records exist) but at the cost of these Focus requirements having nothing to operate on.
