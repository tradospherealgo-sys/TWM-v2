## H. Bugs, inconsistencies, and technical problems

### H-1. Stale shared `focusState` breaks panel interactivity after any non-Dock navigation (confirmed, reproducible, cross-cutting)

**Mechanism.** `app.js:27` holds one module-level `focusState = { mode, focusedId }`. It is reset to `{mode:'overview', focusedId:null}` in **exactly one place**: inside the Floating Command Dock's `onSelect` callback (`app.js:121-124`). Every other way of changing destination — the dev-preview role-switch `<select>`, the Admin ⌘K palette's destination buttons, a More-hub tile's `onFocus` deep-link, direct hash/URL edits, or browser back/forward — calls `TwmRouter.navigate(...)` directly and never touches `focusState`. `renderRoute` (`app.js:117-118`) derives the active mode as `route.panel ? 'immersive' : focusState.mode` — so if the user previously entered Focus mode anywhere (by clicking any panel with an `onFocus` handler) and then arrives at a **different destination** through any path except the Dock, that new destination inherits `mode:'focus'` with a `focusedId` that doesn't exist among its own panels. `layout.css:62-65`'s rule then matches **every** panel on the new screen (`:not(.twm-stage__panel--focused)` matches all of them, since none has that class) — all panels simultaneously dim to 20% opacity **and** get `pointer-events: none`. Compounding this, `stage.js:41` only attaches the click handler `if (panel.onFocus && mode === 'overview')` — since mode is `'focus'`, not `'overview'`, the click listener is never even attached. The destination becomes fully inert until the user clicks a Dock item (the one path that resets the state).

**Reproduction (3 independent, saved, re-run scripts; all evidence fresh this session):**

Direct-hash-navigation repro — [repro_focus_bug.js](V2_AUDIT_EVIDENCE/repro_focus_bug.js), screenshots [bug_repro_1_focus_mode.png](V2_AUDIT_EVIDENCE/screenshots/bug_repro_1_focus_mode.png), [bug_repro_2_stuck_focus_on_new_screen.png](V2_AUDIT_EVIDENCE/screenshots/bug_repro_2_stuck_focus_on_new_screen.png).
2. Admin ⌘K-specific repro (the spec-locked supplementary nav layer) — [verify_cmdk_focus_bug.js](V2_AUDIT_EVIDENCE/verify_cmdk_focus_bug.js), full output in [cmdk_focus_bug_verification.txt](V2_AUDIT_EVIDENCE/cmdk_focus_bug_verification.txt), screenshot [bug_repro_3_cmdk_stuck_focus.png](V2_AUDIT_EVIDENCE/screenshots/bug_repro_3_cmdk_stuck_focus.png): focus `/admin/team`'s Employees panel → ⌘K → Compliance → first Compliance panel renders `{"opacity":"0.2","pointerEvents":"none"}` → a real Playwright click on it times out (`TimeoutError: elementHandle.click: Timeout 4000ms exceeded`).
3. Control-vs-poisoned cascade repro, proving the exact same root cause explains all three originally-failing automated interaction tests (`employee_more_hub_immersive_nav`, `admin_more_hub_immersive_nav`, `admin_command_centre_tile_deeplink`) — [verify_cascade.js](V2_AUDIT_EVIDENCE/verify_cascade.js), full output in [cascade_bug_verification.txt](V2_AUDIT_EVIDENCE/cascade_bug_verification.txt), screenshot [bug_repro_4_cascade_poisoned_more_hub.png](V2_AUDIT_EVIDENCE/screenshots/bug_repro_4_cascade_poisoned_more_hub.png). Result: on a **clean** load, `employee/more`'s first tile click succeeds immediately (control). Clicking any Dock item afterward restores normal clickability.
4. **Ordinary-usage repro via event bubbling (no deliberate "poisoning" step required)** — [verify_smc_bubbling.js](V2_AUDIT_EVIDENCE/verify_smc_bubbling.js), full output in [smc_bubbling_verification.txt](V2_AUDIT_EVIDENCE/smc_bubbling_verification.txt), screenshots [smc_bubbling_check_1_markets_after_connect.png](V2_AUDIT_EVIDENCE/screenshots/smc_bubbling_check_1_markets_after_connect.png) and [smc_bubbling_check_2_trade_screen_state.png](V2_AUDIT_EVIDENCE/screenshots/smc_bubbling_check_2_trade_screen_state.png). On `/client/markets`, every panel (incl. the Watchlist panel) has `onFocus` set and, per `stage.js:43`, the panel element itself carries a `click` listener that calls `panel.onFocus()`. The Watchlist panel conditionally renders a nested `#twm-connect-smc` button (`client.js` `connectBanner()`). Clicking that button to connect an SMC account is an ordinary, spec-intended user action — but the click **bubbles** from the button up through its ancestor panel element, firing the panel's own click listener too. Instrumenting `window.TwmSetFocus` confirms this directly: a single click on `#twm-connect-smc` logs exactly one call, `TwmSetFocus("focus","watchlist")` — called as an unintended side effect, not by any deliberate Focus-mode interaction. The stage class changes to `twm-stage--focus` immediately. Navigating afterward (via plain hash change) to `/client/trade` inherits this stale state; `[data-mode="live"]` computes `pointer-events: none` and a real click on it times out (`TimeoutError: elementHandle.click: Timeout 3000ms exceeded`) — exactly the H-1 symptom, but reached via what a real user would consider a single, unremarkable action (connect an account, then switch tabs), not an edge case or a deliberately engineered sequence.

**Severity and scope.** This is not an edge case: it reproduces through the Admin ⌘K palette, which `06_ADMIN_INTERFACE.md` locks as a required supplementary navigation layer, through plain browser back/forward, which every user has access to, and — most severely — through the single most ordinary Client flow in the whole app (connect your SMC account from Markets, then go trade). It silently breaks interactivity app-wide, across every one of the 24 destinations audited, for the remainder of a session until the user happens to click the Dock. It fully explains all 3 of the automated test timeouts recorded in [V2_TEST_RESULTS.md](V2_TEST_RESULTS.md) — there is one root cause, not three (or four) separate problems.

**Root-cause note on repro #4 specifically:** the underlying defect is still the shared stale `focusState` documented above; the event-bubbling behavior is what makes an *ordinary click* (not just non-Dock navigation) sufficient to set it. This means the bug's practical trigger surface is larger than "any non-Dock navigation" alone — it also includes any click on a nested interactive element inside a panel that itself has `onFocus` set, anywhere in the app. `wireConnectButtons()`/`connectBanner()` in `client.js` is the one shared pattern found that does this, but the defect is structural (missing `event.stopPropagation()` on the nested button, or missing `event.target === panelEl` guard in `stage.js`'s panel click listener) and could recur in any future panel that mixes an `onFocus` handler with nested clickable children.

**Fix location (not applied — audit only, per Step 7):** either reset `focusState` at the top of `renderRoute` whenever `activeDestination` changes from its previous value, or move the reset into `TwmRouter.navigate` itself so every navigation path resets it uniformly, the same way the Dock's callback already does.

Classification: **PARTIALLY IMPLEMENTED** (Focus mode works correctly within a single screen reached via the Dock — the specified behavior — but breaks for every other way of changing screens), tagged **Blocked by missing information: none** — this is a pure code defect, not an open product decision.
